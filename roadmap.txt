=========================================================
ARCHITECTURE STYLE  [CHANGED — reconciled with simplified stack]
=========================================================

[NOTE ON THIS CHANGE] The original version of this prompt specified 12
independent microservices, Kafka event streaming, Redis caching, and
Kubernetes deployment. That has been intentionally simplified to match
the actual tech stack package below: no Kafka, no Redis, no
Docker/Kubernetes. This is a legitimate and defensible architectural
choice for this round — NOT a downgrade — provided the justification is
stated explicitly and consistently everywhere (this prompt, the code,
and eventually the video). The justification:

"A national-scale platform is the eventual target, but a hackathon
qualification round is judged on engineering decision quality, not
infrastructure footprint. We chose a modular monolith with strict
internal module boundaries (mirroring the original microservice split)
so the system is simple to build, test, and demo now, while remaining
decomposable into real microservices later with minimal rework — each
module already has its own package, its own persistence boundary
convention, and communicates internally only through defined
interfaces/events, not through shared mutable state."

Concretely:
- ONE Spring Boot application (helpguru-backend), not 12 deployable
  services.
- Internal module boundaries still mirror the original service list
  (auth, user, incident, resource, decision, dispatch, hospital,
  notification, monitoring, analytics, audit) as separate packages with
  clear public interfaces — this preserves the separation-of-concerns
  story for the video/judges even without physical service separation.
- Inter-module communication happens via direct interface calls plus
  Spring's `ApplicationEventPublisher`/`@EventListener` for
  decoupled, event-driven-style triggers (see DECISION ENGINE below) —
  this is the direct replacement for Kafka's role, scoped honestly to
  "in-process event-driven," not "distributed event-driven."
- If asked "how would this scale to microservices later," the answer is:
  each package's public interface becomes a REST/gRPC contract, and the
  ApplicationEventPublisher calls become Kafka topic
  publishes — the module boundaries were chosen specifically to make
  that migration mechanical, not a rewrite.

=========================================================
SCALABILITY NOTE  [NEW]
=========================================================

Current deployment target: single backend instance, single PostgreSQL
database — appropriate for a hackathon demo and honest about it.

Designed-in scalability path (explain this, don't build it):
1. Stateless backend + JWT (no server-side session) means multiple
   instances behind a load balancer would work today with zero code
   change, if horizontal scaling were needed.
2. Module boundaries (see ARCHITECTURE STYLE) mean the Decision Engine,
   Dispatch, or any single module could be extracted into its own
   service later without touching the others' internals.
3. PostgreSQL can scale vertically first (standard practice), then via
   read replicas for dashboard/analytics read traffic, then via
   partitioning by region_id if/when true national multi-region load
   requires it.
This gives an honest, defensible answer to "how does this scale?"
without claiming infrastructure (Kubernetes, sharded clusters) that
doesn't exist in this build.

=========================================================
CONFLICT PREVENTION & CONCURRENCY STRATEGY  [CHANGED — no Redis]
=========================================================

• Resource Reservation Locking:
  Optimistic locking via a `@Version` column (JPA/Hibernate) on Resource
  and Assignment entities is the PRIMARY mechanism — this is sufficient
  and idiomatic for a single-instance, single-database deployment (no
  distributed lock needed, since there's only one JVM and one DB).
  On a version conflict (`OptimisticLockException`), the Decision Engine
  re-scores and selects the next-best available resource rather than
  failing the incident — conflict becomes a re-optimization trigger, not
  an error state.
  [CHANGED FROM PRIOR VERSION] The earlier design used a Redis
  distributed lock for the reserve/commit window; that's removed since
  it assumed multiple service instances contending across a network.
  In a single-instance monolith, a JVM-level synchronized block or
  Postgres `SELECT ... FOR UPDATE` on the specific resource row during
  the reservation transaction is sufficient and simpler — use
  `SELECT FOR UPDATE` scoped tightly to the reservation transaction only,
  to avoid serializing unrelated reads.

• Idempotency:
  Since there is no Kafka and no message redelivery, classic "duplicate
  event" idempotency is less critical — but idempotency still matters at
  the API layer: dispatch/reservation endpoints should be safe against
  double-submission (e.g., a user double-clicking "Dispatch") via a
  unique constraint (one ACTIVE Assignment per incident_id) so a retried
  HTTP request can't create a duplicate assignment.

• Consistency Model:
  Single PostgreSQL instance with ACID transactions means strong
  consistency is the default and free — the earlier CAP-tradeoff
  discussion (strong vs. eventual consistency across services) mostly
  goes away in this simplified architecture. This is worth stating
  explicitly as a benefit of the modular-monolith choice, not just a
  simplification: "we get correctness by default here, without the
  distributed-systems complexity that would only pay off at a scale this
  round doesn't require."

=========================================================
DECISION ENGINE
=========================================================

Evaluates: Severity, People affected, Distance, Travel time, Traffic,
Road closure, Weather, Hospital capacity, Vehicle availability, Resource
capacity, Operational constraints, Response deadline.

Generates: Priority Score, Resource Suitability Score, Dispatch
Recommendation.

[CHANGED — event trigger mechanism] The engine recomputes assignments
whenever incidents or resource states change, triggered via Spring's
`ApplicationEventPublisher`/`@EventListener` (in-process, synchronous or
`@Async`) rather than a Kafka consumer. E.g., saving an updated
ResourceEntity publishes a `ResourceUpdatedEvent`; the Decision Engine
module listens and re-scores only the incidents plausibly affected by
that resource (same region/proximity), not the entire incident set —
preserving the "targeted re-score, not full recompute" principle even
without a distributed event stream.

[CHANGED — live-state model] Rather than a Redis-backed materialized
view, the Decision Engine reads current state directly from PostgreSQL
via the Resource/Incident repositories, using appropriate indexes
(region_id, status, geo-coordinates) to keep scoring queries fast. This
is honest about the tradeoff: DB-backed reads are slightly slower than an
in-memory cache, but at the transaction volume a single-instance
deployment actually handles, the added complexity of a cache layer isn't
justified yet — call this out explicitly as "premature optimization
avoided," not an oversight.

Backpressure/load shedding: still relevant even without Kafka —
implement priority-ordered processing (a priority queue or ORDER BY
severity in the re-score batch) so CRITICAL incidents are always
re-scored first if the engine falls behind under load.

=========================================================
CACHE  [CHANGED — no Redis]
=========================================================

No standalone cache layer for this round. If caching is needed for
demo-smoothness (e.g., dashboard aggregate queries), use Hibernate's
built-in second-level cache or a simple in-memory `ConcurrentHashMap`/
Spring `@Cacheable` (default simple cache provider) scoped to
read-heavy, low-volatility data only (e.g., region list, static
reference data) — never for resource availability or anything on the
reservation/conflict-prevention path, where staleness could cause a
double-dispatch. This mirrors the original Redis policy's spirit (never
cache the source of truth for reservations) while matching the
simplified stack.
